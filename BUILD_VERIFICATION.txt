Local Baby Monitor v0.6.8 - build verification

Expected verification for the current branch:
- Kotlin sources compile successfully against Android API 36.
- Android resources/layouts compile and link successfully.
- minSdkVersion 26; targetSdkVersion 36; versionCode 16.
- Parent Monitor's live screen is video-first: the picture is edge-to-edge and takes all space not
  used by the header and the control row, and the zoom/light/noise/connection panel is collapsed
  behind a Controls button instead of permanently sharing the screen with the video.
- Tapping the picture enters and leaves fullscreen, which also rotates to landscape so a 16:9 stream
  fills the screen, and holds FLAG_KEEP_SCREEN_ON only while fullscreen. Screen-off monitoring via
  the foreground service is unchanged.
- Parent Monitor includes a persistent alert-level slider from 16% to 100%.
- Parent live monitoring starts a connectedDevice foreground service and holds a partial CPU wake lock while the monitor session is active.
- Noise notifications use a new high-importance channel with sound, vibration, and lock-screen visibility.
- Android 13+ POST_NOTIFICATIONS permission is declared/requested for system notifications.
- Baby noise detection still reuses the existing AudioRecord PCM stream; no second recorder is opened.
- Parent can remotely enable/disable Baby-side sustained-noise detection and receives acknowledged state.
- Parent control writes (torch and noise) are dispatched off the UI thread, and the Baby side sends
  torch state off the service main thread. A socket write on either main thread throws
  NetworkOnMainThreadException, which is a RuntimeException that StreamWriter's IOException handler
  does not catch, so it silently fails the control on the parent and kills the service on the baby.
- Parent can switch the Baby-side flashlight on/off and receives the state the camera actually holds.
- Parent can zoom the Baby-side camera and receives the ratio the camera settled on. The zoom range is
  read from CONTROL_ZOOM_RATIO_RANGE on API 30+ and from SCALER_AVAILABLE_MAX_DIGITAL_ZOOM with a
  centred SCALER_CROP_REGION below it, so a camera that cannot zoom reports unavailable.
- Zoom is applied to the same repeating request as the torch, under the same rules: no template swap,
  no session rebuild, no blocking wait. Slider drags are throttled so the control channel is not
  flooded, and the released position is always sent.
- Torch changes are a FLASH_MODE change on the existing TEMPLATE_RECORD repeating request: no template
  swap, no capture-session rebuild, no CameraManager.setTorchMode() call while the camera is open, and
  no blocking wait on FLASH_STATE. These were the v0.6.2-v0.6.4 failure modes and tools/verify_project.py
  now fails the build if any of them reappears.
- Torch availability comes from FLASH_INFO_AVAILABLE, so a camera without a flash reports unavailable
  instead of offering a control that cannot work.
- No flashlight permission is declared; the torch is driven through the already-open camera session.
- Baby video capture remains on the uninterrupted recording request path.
- Working v0.5.1 Wi-Fi Direct cleanup/PBC/listen-state path is carried forward.
- Rotation-safe stream surface attach/detach remains present.
- App-level PIN/code authentication remains absent.
- GitHub Actions verifies, builds, names, and uploads an installable debug APK on every push.

Physical-device validation still required:
- Remote torch on target hardware: that the light actually lights, that the reported state matches the
  light, and that video keeps streaming uninterrupted across torch on/off. Remote torch was withdrawn in
  v0.6.5 after failing exactly this check, so it is the gating test for this version.
- Torch behaviour across a camera switch and across a stream drop/reconnect.
- Zoom on target hardware: that the picture actually zooms, that video keeps streaming uninterrupted
  while the slider is dragged, and that the reported ratio matches the picture.
- Zoom range reported by the pre-API-30 crop-region path, which cannot be exercised on API 30+ phones.
- Practical alert-level behavior across target-phone microphones.
- Background alert delivery on target OEM firmware.
- Notification behavior with channel settings, Do Not Disturb, and OEM battery policies.
- Battery impact during long monitoring sessions.
